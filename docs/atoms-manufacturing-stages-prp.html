Atoms — Manufacturing Stages CRUD

The Manufacturing Stages section inside Product Details → Project Management → Atoms tab was previously read-only. This implementation makes all 4 stages fully interactive — create, read, update, and delete — writing directly to the database. Uses Notion-style inline editing with no modals.

Backend APIs

atoms_projects.py · port 8002

All endpoints have matching OPTIONS preflight handlers for CORS. * = required field.

Suppliers (global)
GET/api/suppliers/search?q=<term>&limit=<n>
Returns matching suppliers from account_master. Used for inline search dropdown.
POST/api/suppliers
body: { name*, location? } → { supplier_id }. Inserts into account_master. supplier_type / existing_supplier / is_valid intentionally left NULL.
Stage 1 — Supply Identification
POST/api/atoms-projects/{project_id}/suppliers
body: { supplier_id*, supplier_location?, reasons_for_selection? }. Checks for duplicate supplier before insert. Sets status = IDENTIFIED.
PUT/api/atoms-projects/{project_id}/suppliers/{project_supplier_id}
Updates supplier_location and reasons_for_selection only. Company name not editable (comes from account_master).
DEL/api/atoms-projects/{project_id}/suppliers/{project_supplier_id}
Blocked with error if is_finalized_supplier = 1.
Stage 2 — Supply Finalization
PUT/api/atoms-projects/{project_id}/suppliers/{project_supplier_id}/finalize
Transaction: resets all project suppliers → IDENTIFIED, then marks selected → FINALIZED with finalized_date = GETDATE().
Stage Status (all stages)
PUT/api/atoms-projects/{project_id}/stage-status
body: { stage_id, stage_status }. Values: PENDING / IN_PROGRESS / COMPLETED. Upserts fact_project_stage. Sets is_current=1 for IN_PROGRESS, 0 for others.
Stage 3 — Demand Generation: Sales Reachout
POST/api/atoms-projects/{project_id}/demand-generation/sales-reachout
Required: customer_name. Optional: price_grade_expectation, bu_comments, is_converted, reachout_notes, delivered_quantity.
PUT/api/atoms-projects/{project_id}/demand-generation/sales-reachout/{id}
Verifies row belongs to project via JOIN before UPDATE.
DEL/api/atoms-projects/{project_id}/demand-generation/sales-reachout/{id}
Stage 3 — Demand Generation: Digital Marketing
POST/api/atoms-projects/{project_id}/demand-generation/digital-marketing
Required: mode_of_marketing. Optional: buyer_name, marketing_notes, bu_notes, is_converted, order_link.
PUT/api/atoms-projects/{project_id}/demand-generation/digital-marketing/{id}
DEL/api/atoms-projects/{project_id}/demand-generation/digital-marketing/{id}
Stage 4 — Commercialization: Manufacturing Agreement
POST/api/atoms-projects/{project_id}/manufacturing-agreement
Upsert — creates if none exists, updates otherwise. Required: agreement_status. Optional: exclusivity, campaign_quantity, agreement_value, production_start_date, production_end_date, agreement_attachment, agreement_notes.
Stage 4 — Commercialization: Production Details
POST/api/atoms-projects/{project_id}/production-details
Optional: production_quantity, production_start_date, uom, campaign. Supplier auto-assigned from finalized supplier — not user-editable.
PUT/api/atoms-projects/{project_id}/production-details/{id}
DEL/api/atoms-projects/{project_id}/production-details/{id}
Stage 4 — Commercialization: Orders
POST/api/atoms-projects/{project_id}/orders
Optional: customer_name, order_quantity, order_value, cm1_margin, sales_spoc, order_status, order_received_date, order_closure_date, order_notes, uom. Customer name matched against account_master for customer_id.
PUT/api/atoms-projects/{project_id}/orders/{order_id}
DEL/api/atoms-projects/{project_id}/orders/{order_id}

Auto-Creation Logic — Silent Parent Records

Two backend helpers silently create required parent rows so the frontend never needs to — the user just adds child data and the backend handles the rest.

_get_or_create_demand_generation(conn, project_id)

Triggered when adding any Sales Reachout or Digital Marketing entry.

  1. Check if project_demand_generation exists for project_id
  2. If yes → return demand_id
  3. If no → find finalized supplier (falls back to any supplier if none finalized)
  4. INSERT with demand_source='MANUAL', created_by=1
  5. Return new demand_id
_get_or_create_agreement(conn, project_id)

Triggered when adding any Production Detail or Order entry.

  1. Check if project_manufacturing_agreement exists for project_id
  2. If yes → return agreement_id
  3. If no → find finalized supplier
  4. INSERT stub with agreement_status='DRAFT', created_by=1
  5. Return new agreement_id

Key Design Decisions

Inline editing — no modalsNotion-style UX as requested — fast, in-context editing without interrupting the page flow.
Supplier dropdown as fixed portalDropdown rendered with position:fixed + getBoundingClientRect to prevent clipping inside overflow-x-auto table containers.
Parent records auto-createdsupplier_id and demand_source are NOT NULL in demand_generation — can't be left to the user. Backend handles it transparently.
New supplier: NULLs on type/valid colssupplier_type, existing_supplier, is_valid intentionally left NULL. No defaults should be assumed for suppliers created from this flow.
Finalization resets all, then marks oneGuarantees at the DB level that only one supplier per project is ever FINALIZED at a time. Atomic transaction.
canEdit computed from email matchingNo separate permissions table needed — uses existing project assignment data already loaded on the page.
MANAGER included in isAdminUserControl Tower Managers need write access, not just Admins. Updated check: ["ADMIN","MANAGER"].includes(role) for department_id = 7.
Agreement uses upsert — single endpointOnly one manufacturing agreement per project. One endpoint handles both create and update — simpler than separate create/update flows.
